Personal project · AI security

Cyssie

A self-hosted AI assistant designed to combine retrieval, skills, and external tools without treating every model action as implicitly trusted.

Context

A FastAPI-based assistant using RAG, skill-based orchestration, and tool calling, deployed on AWS.

Security question

How should authentication, retrieved context, and tool execution remain bounded when the model can act across multiple components?

Assessment

  • Mapped trust boundaries between the interface, API, retrieval layer, tools, and external services.
  • Reviewed authentication failure paths, secrets handling, tool permissions, and retrieval behavior.

Decision

Keep authentication fail-closed, make capabilities explicit through skills and tools, and preserve observable execution paths for debugging and review.

Evidence

System architecture and implementation notes, authentication tests, retrieval behavior checks, and tool-execution logs.

Sanitized reference case · Secure design

Application Architecture Assessment

A structured review of a critical-system architecture, centered on the complete control path rather than the presence of individual security products.

Context

A business-critical system with user access, system-to-system flows, privileged operations, external connectivity, and sensitive financial data.

Security question

Which access paths reach critical components, what identities and permissions they use, and where preventive or detective controls may be bypassed?

Assessment

  • Mapped entry points, network zones, trust boundaries, service identities, and administrative access.
  • Reviewed authentication, authorization, sensitive operations, logging, monitoring, and data movement.

Decision

Separate business, service, and privileged-access paths; constrain external ingress; and attach authentication, least privilege, logging, and approval evidence to each path.

Evidence

A reference architecture, access-path inventory, control mapping, open-gap list, remediation requirements, and residual-risk record.

Ongoing operational framework · AppSec assurance

Application Security Assurance

A repeatable path from application inventory and new vulnerability information to scoped remediation, acceptance evidence, and closure.

Context

Application, OS, middleware, ownership, and security-control data were fragmented, making new findings difficult to scope consistently.

Security question

When a new finding arrives, which applications are actually exposed, what conditions make it relevant, and what proves remediation is complete?

Assessment

  • Correlate findings with application architecture, technology stack, exposed interfaces, roles, and data.
  • Assess applicability, prerequisites, control coverage, impact, ownership, and remediation priority.

Decision

Use a common evidence model: risk statement, security requirement, acceptance criteria, validation evidence, and residual risk.

Operating flow

Inventory baselineFinding triageImpact scopeRemediationVerify & close

Evidence

Application and technology-stack inventory, control-coverage matrix, scoped remediation tickets, implementation evidence, validation results, and documented exceptions.

This describes an operating framework and evolving area of responsibility. It separates security judgment and acceptance from implementation work performed by application or operations teams.
